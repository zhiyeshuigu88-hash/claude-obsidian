## 1. 背景と目的

### 1.1 解決したい課題

日々の支出が「感覚」でしか把握できておらず、月末になって初めて使いすぎに気づく。
固定費（家賃・サブスク等）と変動費（食費・交際費等）が混ざって記録されるため、
「今月あといくら自由に使えるのか」が即座にわからない。

### 1.2 アプリの目的

**「今日あといくら使えるか」を一目で示し、使いすぎを事前に防ぐ。**

記録すること自体が目的ではなく、記録が意思決定（買う／買わない）に効くことを目指す。

### 1.3 成功の定義（提案）

| 指標 | 目標 |
|---|---|
| 支出入力の所要時間 | 1件あたり10秒以内 |
| 入力継続率 | 3ヶ月後も週5日以上入力している |
| 体感 | 買い物前にアプリを開く習慣がつく |

データモデル上は拡張可能な形にしておく。

### 3.2 主な利用シーン

|---|---|---|---|

## 4. 期間の定義（v0.2で追加・重要）

### 4.1 基本ルール

給料日を起点とした **27日始まり・翌26日終わり** を1期間とする。

```
2026年 8月27日 〜 2026年 9月26日   → 1期間
2026年 9月27日 〜 2026年10月26日   → 1期間
```

### 4.2 なぜ27日が扱いやすいか

27日はすべての月に存在するため、月末日にありがちな例外処理が不要。
（仮に31日始まりだと2月・4月等で破綻し、「その月に存在しない日は月末に丸める」といった
分岐が全体に波及する。27日ならこの問題が発生しない。）

### 4.3 期間の呼称（決定）

**開始月を基準に呼ぶ。`8/27〜9/26` は「8月分」。**

給料を受け取った月の名前をそのまま使う、直感的で説明の要らない方式。

**実装上の注意**: この呼称では、期間の大半（9/1〜9/26 の26日間）が
名前と異なる暦月に属することになる。ラベルだけを見て月を判断するコードを書くと
必ずズレるため、以下を徹底する。

- 内部処理では**ラベルを一切使わず**、必ず `starts_on` / `ends_on` の実日付で判定する
- ラベルは表示専用の文字列として扱う
- UI上は `8月分 (8/27 – 9/26)` のように**必ず実日付を併記**する

特に「9月20日の支出」が「8月分」に集計される点は、
半年後に自分でコードを読み返したときに混乱しやすい。
期間計算ユーティリティのコメントに明記しておく。

### 4.4 給料日が土日祝の場合

実際の振込は前営業日に前倒しになるが、**期間の区切りは27日固定**とする。
振込日に連動させると期間長が月ごとに揺れ、日割り計算が不安定になるため。

### 4.5 実装上の注意

期間計算は必ず**単一のユーティリティ関数に集約**する。

```ts
getPeriod(date)        // 任意の日付が属する期間の開始日・終了日を返す
getRemainingDays(date) // その日を含む、期間終了日までの残日数
```

集計・グラフ・予算・固定費計上のすべてがこの関数に依存する。
各所で `date.getMonth()` を使い始めると必ず境界バグが出る。

**タイムゾーンは Asia/Tokyo に固定**する。UTCで日付を扱うと、
深夜の入力が前日扱いになる事故が起きる。

## 6. 中核となる考え方（最重要）

このアプリの心臓部は「**今日つかえる額**」という1つの数字です。

### 6.1 計算式

```
期間の変動費予算 = 期間予算 − 当期間の固定費合計
残額           = 期間の変動費予算 − 当期間の変動費実績
残日数         = 期間終了日(26日) − 本日 + 1
```

**残額が0以上のとき（通常時）**

```
今日つかえる額 = 残額 ÷ 残日数
```

**残額がマイナスのとき（超過時）**

```
表示は「超過額」= |残額| をそのまま表示。日割りしない。
```

### 6.2 超過時に日割りしない理由（v0.2で決定）

超過額を残日数で割ると、支出がまったく増えていないのに
日が経過するだけで表示額が悪化する。

| 状況 | 超過額 | 残日数 | 日割りすると |
|---|---|---|---|
| 超過した日 | −3,000円 | 10日 | −300円 |
| 5日後（支出なし） | −3,000円 | 5日 | −600円 |
| 9日後（支出なし） | −3,000円 | 1日 | −3,000円 |

何も使っていないのに数字が10倍に悪化する。これは明確な誤情報なので、
超過後は**超過総額をそのまま出す**方式に切り替える。

副次的な効果として、「今日つかえる額」から「超過額」へ**表示の意味が切り替わる**ことが、
それ自体で強い警告シグナルになる。

### 6.3 なぜこの設計か

- **固定費を分母から外す**ことで、自由に裁量できるお金だけを見せられる。
  家賃込みの日割り額は意思決定に使えない。
- **残日数で割り直す**ことで、使いすぎた翌日は自動的に予算が締まり、
  節約した翌日は少し緩む。罰則感がなく自己補正が働く。
- 数字が1つなので迷わない。

### 6.4 表示イメージ

**通常時**

```
┌─────────────────────────┐
│  8月分 (8/27 – 9/26)     │
│    今日つかえる          │
│      ¥ 2,340            │
│  ─────────────          │
│  今日の支出   ¥1,160     │
│  残り 18日               │
│  期間の変動費 ¥42,800    │
│  期間の固定費 ¥98,000    │
└─────────────────────────┘
```

**超過時**

```
┌─────────────────────────┐
│  8月分 (8/27 – 9/26)     │
│    予算を超過中          │
│    − ¥ 3,120            │  ← 赤系表示
│  ─────────────          │
│  今日の支出   ¥1,160     │
│  残り 6日                │
│  期間の変動費 ¥71,120    │
└─────────────────────────┘
```

## 7. 機能要件

### 7.1 支出の登録（変動費）

| 項目 | 内容 |
|---|---|
| 必須入力 | 金額 |
| 任意入力 | カテゴリ、日付（既定=今日）、メモ、店名 |
| 操作目標 | 金額入力 → カテゴリ選択 → 保存 の3ステップ |
| 補助 | よく使う金額・カテゴリのクイックボタン |

**要検討（継続）**: カテゴリを必須にするか任意にするか。
必須にすると分析精度が上がるが入力が重くなる。
→ 提案: 任意。未分類は「その他」に自動集約。後からまとめて分類できる画面を用意。

### 7.2 固定費の管理

| 項目 | 内容 |
|---|---|
| 登録内容 | 名称、金額、支払日、周期、カテゴリ、有効/無効 |
| 周期 | 毎月 / 隔月 / 年1回 / カスタム |
| 自動計上 | 支払日が属する期間に、自動で支出レコードを生成 |

**光熱費について（v0.2で決定）**

光熱費はアプリで扱わない。これにより「毎月あるが金額が変わる費目」の問題が
そもそも発生せず、`is_estimated`（見込み額）フラグや「準固定費」という
第3の分類が不要になった。**データモデルとUIが1段シンプルになる。**

> **注意点**: 予算額の意味が「家計の総支出予算」ではなく
> 「**このアプリで管理する範囲の支出予算**」になる。
> 予算を設定する際、光熱費相当分をあらかじめ差し引いた金額を入れる必要がある。
> UI上に「※光熱費は含みません」の注記を入れることを提案。

**設計上の注意**: 固定費は日次のペース計算に含めない。
期間合計には含めるが、日間合計の表示からは除外するか別枠表示にする。

**期間との関係**: 支払日が27日より前か後かで、どの期間に属するかが変わる。
例えば支払日が「毎月1日」の家賃は `8/27〜9/26` の期間に属する（9/1 が期間内のため）。
支払日が「毎月28日」のサブスクも同じ期間に属する。
この判定も `getPeriod()` に一本化する。

### 7.3 レシート撮影による読み取り（フェーズ2）

| 処理 | 内容 |
|---|---|
| 入力 | カメラ撮影 または 画像アップロード |
| 抽出項目 | 合計金額、日付、店名、（可能なら）品目明細 |
| 確認 | 抽出結果を必ず編集可能な形で提示してから保存 |
| 失敗時 | 手入力にフォールバック。画像だけ添付して後で処理も可 |

**技術選択肢**:

| 方式 | 精度 | コスト | 備考 |
|---|---|---|---|
| Claude API (Vision) | 高。日本語レシートも文脈で解釈可 | 従量課金 | 構造化JSONで返させやすい |
| Google Cloud Vision OCR | 文字認識は高精度 | 無料枠あり | 意味づけは自前実装が必要 |
| ブラウザ内OCR (Tesseract.js) | 低〜中 | 無料 | 日本語レシートは厳しい |

→ 提案: Claude API。品目明細まで一度に構造化できる利点が大きい。
コストが気になる場合は「合計金額のみ抽出」に絞れば入力トークンを抑えられる。

**要検討（継続）**: レシート画像そのものを保存するか。保存するならストレージ容量とコスト。

### 7.4 予算管理

- 期間予算の設定（27日始まりの期間ごと）
- カテゴリ別予算（フェーズ2）
- 予算に対する消化率の表示
- 使いすぎペース時の警告表示

**要検討（継続）**: 警告の出し方。
- 案A: 残額の色を変えるだけ（控えめ）
- 案B: バナー表示
- 案C: プッシュ通知
→ 提案: まず案A。超過時に表示の意味自体が切り替わるので、これだけでも十分効く可能性がある。

### 7.5 集計・プレビュー

| 表示 | 内容 |
|---|---|
| 日間合計 | 当日の変動費合計。過去日付も参照可 |
| 期間合計 | 固定費 / 変動費 / 総額の3つを分けて表示 |
| カテゴリ別内訳 | 期間単位。円グラフまたは横棒グラフ（フェーズ2） |
| 推移 | 日別の支出棒グラフ（フェーズ2） |

すべての集計は**カレンダー月ではなく27日始まりの期間**を単位とする。
UIのラベルには常に実日付を併記する。

### 7.6 支出一覧・編集

- 日別・期間別の一覧表示
- 編集・削除
- カテゴリ・期間でのフィルタ
- 未分類支出の一括分類

### 7.7 認証

「どこからでも使える」＝インターネット上に置く以上、認証は必須。

- メール + パスワード、または OAuth（Google）
- 個人利用のため新規登録の開放は不要（自分のアカウントのみ）

**要検討（継続）**: 自分専用なら登録機能を閉じてしまうのが安全。

## 9. データモデル（案）

```
users
  id, email, created_at

user_settings                    -- v0.2で追加
  user_id, period_start_day      -- 既定 27。将来変更できるよう設定として持つ
  timezone                       -- 'Asia/Tokyo'

budget_periods                   -- v0.1の budgets を改称・変更
  id, user_id,
  starts_on,                     -- 例: 2026-08-27
  ends_on,                       -- 例: 2026-09-26
  label,                         -- 例: '2026-08'（開始月基準）。表示専用。判定には使わない
  amount,                        -- この期間の予算額（光熱費は含まない）
  created_at

categories
  id, user_id, name, color, icon, sort_order, is_archived

fixed_costs
  id, user_id, name, amount, category_id,
  cycle          -- monthly / bimonthly / yearly / custom
  payment_day    -- 支払日
  starts_on, ends_on, is_active
  ※ is_estimated は光熱費除外により不要になったため削除

expenses
  id, user_id, amount, category_id, spent_on,
  type           -- 'fixed' | 'variable'
  fixed_cost_id  -- 固定費から自動生成された場合の参照
  store_name, memo, receipt_id, created_at

receipts
  id, user_id, image_url, ocr_status, ocr_raw_json, created_at

receipt_items          -- フェーズ2、品目明細を取る場合
  id, receipt_id, name, amount, quantity
```

### 設計メモ

- `expenses` に固定費・変動費を**同一テーブル**で持ち、`type` で区別する。
  合計計算が1クエリで済む。分けるとUNIONだらけになる。
- `budget_periods` に開始日・終了日を**実データとして保存**する。
  毎回計算で求めると、将来 `period_start_day` を変えたときに
  過去の期間定義まで遡って変わってしまう。実日付を持てば履歴が固定される。
- 固定費の自動計上は「マスタ（fixed_costs）から実績（expenses）を生成する」構造。
  マスタの金額を後から変えても過去の実績は動かない。これは重要。
- `period_start_day` を設定として持つのは、転職等で給料日が変わる可能性への保険。
  MVPでは 27 固定でUIに出さなくてよい。

**要検討（継続）**: 固定費の自動計上をいつ実行するか。
- 案A: 定期実行（Vercel Cron 等）で毎日チェック
- 案B: ユーザーがアプリを開いたときに「未計上の固定費」を検出して生成
→ 提案は案B。個人利用なら定期実行のインフラを持つ必要がない。

## 11. 技術構成（案）

| 領域 | 選択 | 理由 |
|---|---|---|
| フレームワーク | Next.js (App Router) | 慣れているスタック。PWA化も容易 |
| ホスティング | Vercel | 無料枠で十分。デプロイが速い |
| DB / 認証 / ストレージ | Supabase | Postgres + Auth + Storage + RLS が1つで揃う |
| ORM | Drizzle ORM | 型安全。Supabaseとも問題なく併用可 |
| UI | Tailwind CSS + shadcn/ui | 実装速度重視 |
| 日付処理 | date-fns + date-fns-tz | 期間計算とタイムゾーン固定に必要 |
| グラフ | Recharts | React親和性が高い |
| OCR | Claude API (Vision) | 構造化抽出まで一気にできる |

### 注意点

- OCRのAPIキーは**必ずサーバー側（Route Handler）で扱う**。
  クライアントから直接叩くとキーが漏れる。
- SupabaseのRLSは最初から有効にする。後付けは事故のもと。
- 期間計算ユーティリティには**最初にテストを書く**。
  27日境界・うるう年・月またぎは目視確認では漏れる。

## 付録: あえて入れなかった機能とその理由

| 機能 | 理由 |
|---|---|
| 光熱費の管理 | v0.2で除外決定。これにより分類が2種類に保たれ、モデルが単純化した |
| 銀行・カード連携 | 実装コストが桁違い。個人開発では金融機関APIの利用が現実的でない |
| 割り勘・共有 | 目的（自分の使いすぎ防止）から外れる |
| 詳細な資産管理 | 家計簿アプリの肥大化パターン。別アプリにすべき |
| ゲーミフィケーション | 続かない原因は「入力が面倒」であって「楽しくない」ではない |
